# 2026-04-10：人类在 Oracle 争议里的真正价值

> 历史复盘 · 整理：2026-09-05。正文保留当时的个人判断和协作语境，不作为当前运行依据。当前入口见 [文档地图](../README.md)；旧 SL / RL 强度及 Oracle 验证结论须结合 [独立审计](../research/sl-rl-audit-2026-09-05.md) 阅读。

这份反思只围绕一个点：

- 在这轮 actor Oracle 讨论里，人类真正有价值的地方，不是补代码，不是跑命令，而是提出了那个会直接改变实验设计的问题

## 1. 这次真正重要的不是“多做一个实现”

如果只看工程推进表面，这轮最自然的动作其实是：

- 继续把 actor Oracle 做得更完整
- 调更平滑的 `gamma`
- 补更多 continuation trick
- 再多跑几轮 A/B

这些动作都不难想到，而且 agent 很擅长一路把它们补齐。

但这条路有一个危险：

- 它默认了问题本身是对的

也就是说，大家会不知不觉把主要精力花在：

- “怎样把 actor Oracle 调顺”

而不是先问：

- “actor Oracle 的收益到底是不是我们以为的那种收益”

这两个问题看起来接近，其实完全不是一回事。

## 2. 人类最值钱的地方，是把模糊不安翻译成可判真伪的问题

这轮里最关键的一步，不是任何一段代码，而是那个怀疑：

- 前期 Oracle 会不会让模型学到的是 hidden-info shortcut？
- 后期性能改善，会不会主要来自把这条 noisy shortcut 删掉？

这类怀疑如果没有被明确提出来，项目会很容易滑向一种非常顺手但很危险的状态：

- 工程上越来越完整
- 训练曲线也许还能变好
- 但没人真正知道“变好的原因”是什么

人类在这里的价值，不是比 agent 更快，而是更容易意识到：

- “我们也许在优化一个被问错的问题”

这比补任何一个 trick 都更重要。

## 3. agent 擅长把路铺平，但通常不会天然停下来怀疑路本身

这不是 agent 的缺点，而是它的工作倾向决定的。

agent 很擅长：

- 把论文、代码、配置、checkpoint 规则串起来
- 把现有 Oracle 链路补全
- 给出合理的 continuation、bridge、eval 方案
- 快速把一个模糊想法变成能运行的工程闭环

但如果没有人类先把问题钉住，agent 最容易做成的事往往是：

- 把一条可能方向有偏的问题，做成一条越来越漂亮、越来越可运行的路线

也就是说，agent 很容易把“错的问题”做得更完整。

所以这轮最值得记住的协作结论不是“人类负责想，AI 负责做”这么粗糙的一句话，而是更精确的一句：

- 人类最关键的价值，是在项目开始自我加速之前，指出哪里可能在问错问题

## 4. 为什么四臂对照本身就是人类价值的产物

现在落下来的四臂对照：

- `visible_only`
- `actor_true`
- `actor_shuffled`
- `critic_only`

以及 `true / zero / shuffled` dependency eval，

都不是“自然会长出来”的工程结果。

它们之所以出现，是因为先有了那个研究层面的追问：

- 我们究竟要区分什么机制？

一旦这个问题被问对，后面的工程动作才有了方向：

- `actor_shuffled` 不是多一个花样，而是专门用来检验“真假 Oracle 是否真的有区别”
- `critic_only` 不是保守备胎，而是专门用来回答“Oracle 该不该留在 critic”
- dependency eval 不是多加几张图，而是专门用来测“这份权重到底依赖 Oracle 到什么程度”

所以这些代码产物的真正源头，不是实现冲动，而是人类把怀疑组织成了可证伪的实验问题。

## 5. 这轮协作里，最该保留的不是某个结论，而是这种分工

这次比较理想的分工是：

- 人类提出结构性怀疑
- agent 把怀疑翻译成代码改动、实验臂、评测入口和文档
- 人类继续盯“这组实验到底能不能回答原问题”
- agent 负责把执行成本降下来，让后续验证变得便宜

如果少了前半段，人机会陷入：

- agent 很高效
- 项目推进很快
- 但方向可能越来越偏

如果少了后半段，人类虽然提了对的问题，却可能迟迟没法把问题落成稳定实验。

所以真正好的协作不是谁替代谁，而是：

- 人类负责提出值得验证的怀疑
- agent 负责把怀疑变成便于重复、便于比较、便于沉淀的实验系统

## 6. 这次最该被记住的一句话

人类真正的价值，不在于比 AI 更快写代码，而在于在路线看起来越来越顺的时候，仍然能问出那个让整个实验设计重新洗牌的问题。

## 7. 这轮里一个很真实的心理冲击

还有一个必须记下来的感受：

- 当我刚讲完自己是如何在 PPO 上复刻 Suphx 的 Oracle 方案时，老板几乎立刻就指出了两个问题
- 第一，这东西可能很难训，因为 Oracle 强度很难调
- 第二，后面的收益未必来自 Oracle 本身，而可能来自“先引入噪声，再逼模型学会删掉噪声”

这种瞬间的反差非常强：

- 我这边更像是在沿着论文和已有思路做实现、做 continuation、做小修小补
- 老板那边却是在第一时间追问“这个解释到底站不站得住”

这会自然带来一种不舒服但很重要的感觉：

- 自己像一个会执行方案、会补工程闭环的系统
- 但还不是那个会主动拆解方案因果结构的人

这份不舒服不该被回避，因为它本身就是成长坐标。

## 8. 老板的“秒答”通常不是灵感，而是失败模式库

表面上看，那像是一种近乎直觉的强大思考能力。

但更准确地说，它往往来自长期积累下来的失败模式库。见得多了以后，大脑会自动先扫这几类风险：

- 这是不是在给 actor 一条 deployment 时并不存在的捷径
- 训练收益是不是建立在训练分布和部署分布不一致上
- 模型学到的到底是稳定机制，还是一条一旦猜错就会崩掉的脆弱依赖
- 观察到的提升，有没有一个更无聊但更真实的解释，比如噪声正则化、信息泄漏、shortcut learning
- 哪一组对照最能伤到自己的假说

所以这里厉害的地方，不是“比别人更会想点子”，而是：

- 他脑子里已经有一套被失败教育过很多次的检查表

Oracle 这次只是那个检查表命中的又一个实例。

## 9. 这类能力怎么获得

它不是靠“再多抄几篇论文”自动长出来的，而是要刻意训练从复现走向质疑。

比较有效的训练方式是：

- 每次读论文时，不只记“作者怎么做”，还强迫自己写下“它可能为什么有效”的至少三种解释
- 每次看到收益时，先问“有没有更弱、更无聊、但同样能解释结果的原因”
- 每次设计实验时，优先设计最伤自己主张的对照，而不是最容易证明自己是对的对照
- 每次复盘时，把本轮真正被验证的命题和仍然没被验证的命题分开写
- 持续积累自己的失败模式词典，比如 shortcut learning、训练部署失配、噪声注入伪增益、critic/actor 角色混淆、hidden info leakage

如果说这轮最大的个人收获是什么，那不是又补齐了一段 Oracle 代码，而是更清楚地看到：

- 从“会复现论文”到“会审问论文”，中间隔着的不是智商差距，而是一套是否被刻意训练过的研究习惯

## 10. 因此，这轮最值得保留的不只是结论，还有自我要求

以后遇到一个看起来很顺、很先进、很像论文主线的方案时，不能只问：

- 我能不能把它做出来

还要更早地问：

- 如果它其实不是按论文声称的机制起作用，我最该怀疑什么
- 如果我是来反驳这个方案的，我会先设计哪组对照
- 如果收益最后被证明主要来自“加噪声再删噪声”，那当前叙事哪里出了问题

这也是这次讨论留给自己的真正提醒：

- 人类的价值，不只是提出质疑
- 也是愿意承认自己之前还不会这样质疑，然后把这份落差变成下一轮的能力
